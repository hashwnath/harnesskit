## Application Bootability

Every service MUST be bootable from a clean worktree in 2 commands:

```bash
pip install -r requirements.txt
python -m app
```

If boot fails, `harnesskit doctor` MUST surface the root cause.

### Health Endpoints

| Path | Expected Response | Purpose |
|------|-------------------|---------|
| `/healthz` | `200 { "status": "ok" }` | Liveness probe — app process is running |
| `/readyz`  | `200 { "ready": true }` | Readiness probe — PostgreSQL, Redis, and Celery are reachable |

> **Agents:** After ANY infrastructure change, verify the app boots and health endpoints respond before marking a task complete.

## Flash Sale Handling

ShopWave must handle **10x normal traffic** during flash sales without downtime.

| Mechanism | Purpose |
|-----------|---------|
| **Redis rate limiting** | Throttle requests per-user during traffic spikes |
| **Redis cart storage** | Offload cart state from PostgreSQL during peak load |
| **Aggressive catalog caching** | Redis-cached product data to absorb read traffic |
| **Inventory reservation** | Atomic stock decrement to prevent overselling |
| **Auto-scaling** | Horizontal scaling of FastAPI and Celery workers |
| **Connection pooling** | SQLAlchemy pool with overflow to handle burst DB connections |

### Flash Sale Sequence

1. Rate limiter checks per-user request budget (Redis)
2. Catalog reads served from Redis cache (bypass PostgreSQL)
3. Cart operations go directly to Redis
4. Checkout atomically reserves inventory (PostgreSQL `SELECT FOR UPDATE`)
5. Payment delegated to Stripe (off-platform load)
6. Order confirmation via Celery task (async, non-blocking)

## Failure Modes & Mitigations

| Failure | Impact | Mitigation |
|---------|--------|------------|
| PostgreSQL connection lost | Orders and catalog unavailable | Connection pool retry + circuit breaker; catalog falls back to Redis cache |
| Redis connection lost | Carts inaccessible, rate limiting disabled | Graceful degradation — fall back to DB-backed sessions; disable rate limiting safely |
| Stripe API timeout | Payments cannot process | Timeout with retry (idempotency keys); show "try again" to user; Celery retry queue |
| Stripe webhook delivery failure | Order status not updated | Stripe retries webhooks; reconciliation Celery task checks pending orders |
| S3/Minio unavailable | Image uploads fail | Queue uploads in Celery for retry; serve cached/placeholder images |
| Celery worker crash | Async tasks (emails, retraining) delayed | Celery auto-restart; tasks are idempotent and retryable |
| OOM on API process | Request failures, pod restart | Memory limits per process; monitor with metrics; no unbounded query results |
| Inventory race condition | Overselling during flash sale | `SELECT FOR UPDATE` with row-level locking; atomic decrement |

## Deployment Safety

- **Zero-downtime required** — rolling deploys with health-check gates
- **Rollback procedure:** Revert last merge commit, CI auto-redeploys previous image
- **Canary threshold:** 5% traffic for 10 minutes, auto-rollback if error rate > 1% or p95 > 500ms
- Run `harnesskit enforce` in CI — block merge on architecture violations
